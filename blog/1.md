# The Case for Monorepos in the Age of AI-Assisted Software Development

AI-assisted software development is changing more than how quickly developers write code. It is changing which architectural decisions make sense.

For years, software architecture was largely optimized around human developers. We cared about reducing cognitive load, separating teams, minimizing coupling, and choosing technologies that balanced development speed with long-term safety.

AI coding agents introduce another participant into the development process: a machine that can reason across a codebase, modify multiple files, run tests, inspect errors, and iteratively improve an implementation.

That changes the value of architecture.

In an AI-assisted development environment, **context, explicit contracts, and machine-verifiable constraints become increasingly important**.

This makes the monorepo, combined with strongly typed languages and a highly integrated application stack, particularly compelling.

## The Monorepo Becomes More Valuable

A monorepo is not inherently better than a collection of repositories. There are legitimate reasons to separate projects: organizational boundaries, security requirements, independent ownership, radically different deployment lifecycles, and extremely large codebases.

But AI-assisted development changes one of the historical tradeoffs.

A coding agent performs better when it can see the relationships between the systems it is modifying.

Consider a feature that touches:

* a mobile application
* a web application
* an API
* a database model
* authentication
* shared UI components
* infrastructure
* tests

In a multi-repository architecture, the agent may need to infer these relationships across repository boundaries.

In a monorepo, the relevant context can exist in one place.

```text
/apps
  /mobile
  /web
  /api

/packages
  /ui
  /database
  /types
  /validation
  /config

/infrastructure
  /terraform

/tests
```

The repository becomes more than a collection of source files. It becomes a representation of the application as a whole.

That is valuable to both humans and AI agents.

## Context Is Becoming an Architectural Resource

One of the biggest advantages of AI coding agents is their ability to reason across large amounts of context.

A developer might understand that changing a database schema requires corresponding API and frontend changes. An AI agent can potentially discover those dependencies directly from the repository.

For example:

```text
Database schema
      ↓
ORM types
      ↓
API contract
      ↓
Frontend client
      ↓
UI
      ↓
Tests
```

When these components live together, an agent can inspect the entire dependency chain before making a change.

This creates a simple principle:

> **The more relevant context an AI agent can reliably access, the less it needs to guess.**

A monorepo does not automatically make an AI agent better. Poorly structured repositories can still be difficult to understand.

But a well-organized monorepo gives the agent something extremely valuable: **local context**.

Instead of asking an agent to understand a distributed system through documentation and repository references, much of that information is directly available in the codebase.

## Strong Typing Has a New Advantage

The argument for strongly typed languages has traditionally been about software correctness.

Types help developers catch mistakes before runtime. They make APIs more explicit, improve tooling, and make large codebases easier for teams to maintain.

AI-assisted development adds another benefit.

**Types provide constraints for the coding agent.**

Consider an API that returns:

```ts
type User = {
  id: string
  name: string
  email: string
}
```

If a frontend component expects `email` to exist and an agent changes the API to remove it, the compiler can immediately expose the resulting breakage.

The compiler effectively becomes a second layer of verification for the agent's work.

This creates a useful relationship:

```text
AI Agent
   ↓
Generates implementation
   ↓
Compiler
   ↓
Finds contract violations
   ↓
AI Agent
   ↓
Corrects implementation
```

The agent does not need to get everything right on its first attempt.

It needs a strong feedback loop.

## TypeScript Is Particularly Interesting

For a full-stack application, using TypeScript across the majority of the application can dramatically reduce the number of translation layers between systems.

A typical architecture might look like:

```text
React Native / Expo
        ↓
      tRPC
        ↓
   TypeScript API
        ↓
     Prisma
        ↓
   PostgreSQL
```

The same language can be used throughout the application.

This does not eliminate runtime errors or make testing unnecessary. TypeScript types disappear at runtime, and external inputs still require validation.

But it does create a shared compile-time model of the application.

That model is especially useful to coding agents.

## API Contracts Become Critical

The frontend and backend are two sides of the same product.

If the API contract is implicit, an AI agent has to infer it.

If the API contract is represented directly in code, the agent can inspect it, use it, and receive compiler feedback when it violates it.

This is one reason a TypeScript-native RPC system such as tRPC is attractive for this architecture.

The goal is not simply to avoid writing REST endpoints.

The goal is to make the relationship between the client and server explicit and machine-checkable.

```text
Client
  │
  │ typed contract
  ↓
tRPC
  │
  │ typed contract
  ↓
Server
```

That becomes particularly powerful when the client, server, shared types, and tests all live in the same repository.

## Runtime Validation Still Matters

Static types are not enough.

TypeScript can tell the developer that a function expects a string, but it cannot guarantee that an HTTP request actually contains a string.

Runtime validation tools such as Zod complement TypeScript by validating data at runtime.

This creates two layers of protection:

```text
Static contract
     ↓
TypeScript

Runtime contract
     ↓
Zod
```

The combination is substantially stronger than relying on either one independently.

For AI-generated code, this distinction is important.

The agent can satisfy the compiler while still creating an unsafe runtime boundary. Runtime schemas provide another layer of machine-verifiable constraints.

## The Repository Becomes a System of Contracts

This leads to a broader architectural idea.

A modern monorepo can contain many different types of contracts:

```text
TypeScript
    → application contracts

tRPC
    → API contracts

Zod
    → runtime contracts

Prisma
    → database contracts

Database migrations
    → schema evolution

Tests
    → behavioral contracts

Terraform
    → infrastructure contracts

CI/CD
    → deployment contracts
```

The more of the application that is explicitly represented this way, the less an AI agent needs to infer.

That is arguably more important than simply giving the agent more tokens or a larger context window.

## AI Coding Changes the Optimization Target

Traditional development often optimizes for developer ergonomics.

A developer might choose a dynamically typed language because it allows them to move quickly and write less code.

That tradeoff changes when an AI agent is writing much of the code.

The human may no longer be optimizing for typing speed.

Instead, the human is optimizing for:

* clarity
* constraints
* feedback
* correctness
* maintainability
* machine-readable relationships

The question becomes less:

> How quickly can I write this?

and more:

> How reliably can an AI agent modify this system without breaking it?

This is a fundamentally different optimization target.

## The Compiler Becomes Part of the AI Feedback Loop

A productive AI coding workflow looks less like:

```text
Prompt
  ↓
Code
  ↓
Done
```

and more like:

```text
Prompt
  ↓
Agent analyzes repository
  ↓
Agent modifies code
  ↓
Type checking
  ↓
Tests
  ↓
Linting
  ↓
Build
  ↓
Errors returned to agent
  ↓
Agent modifies code again
```

This is an iterative engineering loop.

The architecture should therefore make feedback cheap and reliable.

A monorepo with shared types and strong contracts is well suited to this model because a change in one package can immediately expose consequences elsewhere.

## Shared Packages Become More Important

A monorepo also makes it natural to extract common functionality into packages.

For example:

```text
/packages
  /ui
  /types
  /validation
  /database
  /config
  /auth
```

The mobile application, web application, and backend can consume these packages directly.

This reduces duplicated implementations and gives the AI agent a single source of truth.

Instead of having three slightly different versions of a type or validation rule, there can be one shared implementation.

That matters because duplicated logic creates ambiguity.

When an agent encounters three versions of the same concept, it has to determine which one is authoritative.

A shared package removes that question.

## Monorepos Also Improve Refactoring

Large refactors are particularly interesting in AI-assisted development.

Suppose a database field changes from:

```ts
user.username
```

to:

```ts
user.handle
```

In a strongly typed monorepo, the consequences can propagate through:

```text
Database
    ↓
Prisma
    ↓
tRPC
    ↓
Shared types
    ↓
Mobile
    ↓
Web
    ↓
Tests
```

The compiler can identify many affected locations.

An AI agent can then work through those failures systematically.

Instead of manually searching the entire system and hoping every reference was found, the development environment itself helps identify the dependency graph.

## This Does Not Mean "AI Can Replace Engineering"

There is an important limitation.

Strong typing, monorepos, and automated tests do not make AI-generated software automatically correct.

An agent can still:

* misunderstand requirements
* implement incorrect business logic
* choose poor abstractions
* introduce security vulnerabilities
* create inefficient database queries
* write inadequate tests
* make architectural decisions that compile perfectly

The goal is not to eliminate engineering judgment.

The goal is to make the system **more difficult to break accidentally**.

AI agents should be given freedom within a system that provides strong constraints and feedback.

## The Emerging Architecture

Putting these ideas together produces a compelling baseline architecture:

```text
                    Monorepo
                       │
        ┌──────────────┼──────────────┐
        │              │              │
     Mobile           Web           Backend
   React Native      React          TypeScript
      Expo             │              │
        │              │             tRPC
        │              │              │
        └──────────────┼──────────────┘
                       │
                 Shared Packages
                       │
          ┌────────────┼────────────┐
          │            │            │
       TypeScript     Zod        Prisma
          │            │            │
          └────────────┼────────────┘
                       │
                  PostgreSQL
```

Infrastructure can then exist alongside the application:

```text
/infrastructure
    /terraform
```

And CI/CD can enforce the system's contracts:

```text
Git
 ↓
CI
 ├── Type checking
 ├── Tests
 ├── Linting
 ├── Builds
 └── Infrastructure validation
 ↓
Deployment
```

The result is not simply a monorepo.

It is a **machine-readable application ecosystem**.

## A New Definition of Full-Stack

The traditional definition of full-stack development generally refers to the application layers:

```text
Frontend
Backend
Database
```

That definition is becoming incomplete.

A production application also includes:

```text
Application
Database
Infrastructure
Deployment
Testing
Observability
Security
Operations
```

In an AI-assisted development environment, these systems should increasingly be treated as part of the same engineering context.

The repository should describe not only what the application does, but also how it is built, deployed, tested, and operated.

## The Core Principle

The most important architectural principle is not "always use a monorepo."

It is:

> **Optimize the software system for both human understanding and machine reasoning.**

A good architecture gives AI agents:

1. **Context** — the relevant systems exist together.
2. **Contracts** — relationships are explicitly represented.
3. **Constraints** — types and schemas limit incorrect implementations.
4. **Feedback** — compilers, tests, and CI expose mistakes.
5. **Reproducibility** — infrastructure and deployment are represented as code.
6. **Extensibility** — specialized infrastructure can be introduced when actual requirements justify it.

The monorepo is one way to achieve this.

Strong typing is another.

Shared contracts, automated testing, infrastructure-as-code, and CI/CD complete the feedback loop.

The result is an architecture where the AI agent is not simply generating code in isolation. It is operating inside a system that continuously tells it whether its changes are compatible with the rest of the application.

That may ultimately be the more important shift brought by AI-assisted software development:

**We are no longer optimizing only for how humans write software. We are beginning to optimize for how humans and machines can reason about software together.**
