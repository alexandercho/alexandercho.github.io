# Building Production AI Applications on a TypeScript Monorepo

In a previous article, I argued that AI-assisted software development changes the architectural tradeoffs of modern application development.

A monorepo gives coding agents more context. Strong typing gives them constraints. Shared packages create common contracts. CI/CD provides automated feedback. Infrastructure-as-code makes the environment itself part of the codebase.

The next question is what happens when the application being built is itself an **AI application**.

An AI application introduces another set of infrastructure requirements: model providers, prompts, retrieval, embeddings, vector search, evaluations, tracing, token usage, and increasingly sophisticated agent workflows.

The architecture should not require abandoning the principles of the underlying application.

Instead, AI infrastructure can become another layer of the same ecosystem.

## The Core Stack

A production-oriented AI application can begin with:

```text id="j6y8wq"
React Native / Expo
        ↓
      tRPC
        ↓
   TypeScript API
        ↓
      Prisma
        ↓
   PostgreSQL
        │
        └── pgvector

AI Layer
├── LangChain
├── LangGraph
└── Langfuse

Observability
├── OpenTelemetry
├── Prometheus
├── Tempo
├── Loki
└── Grafana

Infrastructure
└── Terraform
        ↓
       AWS
```

The important characteristic is that the AI layer does not need to become an isolated Python system with an entirely separate architecture.

It can remain part of the same application ecosystem.

---

# AI Becomes Another Application Layer

A useful way to think about AI infrastructure is as another layer between the API and the data.

```text id="y7xv6q"
React Native / Web
        ↓
      tRPC
        ↓
   Application
        ↓
   ┌────┴─────┐
   ↓          ↓
Database      AI
   │          │
   ↓          ↓
PostgreSQL  Models
   │          │
pgvector   LangChain
              │
           LangGraph
```

The AI system can use the same authentication, database, API, infrastructure, and observability systems as the rest of the application.

This has an important consequence:

> **AI functionality does not need to become a separate application architecture.**

It can become a capability inside the existing one.

---

# PostgreSQL Can Become the Starting Point for AI Data

One of the easiest mistakes in an AI application is introducing specialized infrastructure too early.

An AI application might eventually require multiple databases and specialized systems.

But an initial architecture does not necessarily need them.

PostgreSQL can already handle:

* application data
* user data
* conversation history
* AI metadata
* documents
* embeddings
* relational associations

With pgvector, vector embeddings can be stored alongside the application's existing relational data.

Conceptually:

```text id="6d5v0s"
PostgreSQL
│
├── users
├── organizations
├── conversations
├── messages
├── documents
├── chunks
├── embeddings
└── AI metadata
```

The major advantage is simplicity.

A document can be associated with a user, organization, permission model, or application object using ordinary relational relationships while also having a vector representation.

That makes retrieval systems much easier to integrate into the rest of the application.

---

# Retrieval-Augmented Generation

A typical retrieval-augmented generation system can then look like:

```text id="5r5n3p"
User
 ↓
tRPC
 ↓
AI Service
 ↓
Create embedding
 ↓
pgvector similarity search
 ↓
Retrieve relevant chunks
 ↓
Construct context
 ↓
LLM
 ↓
Response
```

The database is doing more than storing application state.

It is becoming part of the model's context pipeline.

This is particularly useful when retrieval needs to respect application-level permissions.

For example:

```text id="2e3y4k"
User
 ↓
Organization
 ↓
Authorized documents
 ↓
Vector search
 ↓
Relevant chunks
 ↓
LLM
```

Instead of treating the vector database as an independent collection of documents, retrieval can remain connected to the application's authorization model.

That is one of the strongest arguments for starting with pgvector when it satisfies the workload.

---

# Embeddings Are Data, Too

An embedding should not be treated as some mysterious AI artifact.

At the application level, it is another representation of data.

For example:

```text id="u7s6t1"
Document
   │
   ├── original content
   ├── metadata
   ├── permissions
   └── embedding
```

That means the same application can maintain the relationship between:

* a document
* its owner
* its permissions
* its chunks
* its embedding
* the model used to create it
* the time it was generated

This metadata becomes increasingly valuable as models and embedding systems evolve.

---

# LangChain Provides the AI Application Primitives

LangChain can sit above the model providers and retrieval infrastructure.

Instead of writing every model interaction manually, the application can construct reusable AI components.

For example:

```text id="2qlb6c"
Application
     ↓
LangChain
     ↓
Model provider
```

LangChain can also interact with:

```text id="n0g8kp"
Tools
Retrievers
Models
Prompt templates
Structured outputs
Memory
Agents
```

The important architectural principle is to avoid allowing the AI framework to become the architecture itself.

The application should still own:

* authentication
* authorization
* business logic
* persistence
* API contracts
* domain models

LangChain should provide AI-specific primitives within those boundaries.

---

# LangGraph for Stateful Agents

Simple AI applications can often be represented as:

```text id="f4r0pw"
Input
 ↓
Prompt
 ↓
Model
 ↓
Output
```

Agents become more complicated.

They might need to:

```text id="j3z2wa"
Receive request
      ↓
Determine intent
      ↓
Retrieve information
      ↓
Call tool
      ↓
Inspect result
      ↓
Reason again
      ↓
Call another tool
      ↓
Generate response
```

LangGraph provides a way to represent these workflows as explicit stateful graphs.

That fits naturally with the broader architecture philosophy.

Instead of having a large opaque agent function, the workflow can become an explicit graph of states and transitions.

```text id="5p6g9v"
                ┌──────────┐
                │  Input   │
                └────┬─────┘
                     ↓
                ┌──────────┐
                │  Agent   │
                └────┬─────┘
                     ↓
              ┌──────┴──────┐
              ↓             ↓
           Retrieve       Tool
              │             │
              └──────┬──────┘
                     ↓
                 Evaluate
                     ↓
                  Response
```

This becomes especially important when the system needs to be observed and evaluated.

---

# Langfuse Becomes the AI Observability Layer

Traditional application observability tells you things such as:

* an API request was slow
* a database query failed
* a server crashed
* a service returned an error

AI applications need additional information.

You may need to know:

* which model was called
* which prompt was used
* how many tokens were consumed
* what tools were invoked
* what retrieval context was supplied
* how long generation took
* what the model returned
* whether an evaluation passed
* how much a request cost

This is where an AI-specific observability platform such as Langfuse becomes valuable.

Conceptually:

```text id="9y1v1f"
AI Application
      │
      ├── Model calls
      ├── Prompts
      ├── Retrieval
      ├── Tool calls
      ├── Agent traces
      └── Evaluations
              │
              ↓
           Langfuse
```

Langfuse provides the AI-specific view that conventional infrastructure observability does not provide by itself.

---

# OpenTelemetry Still Matters

Langfuse does not eliminate the need for conventional observability.

An AI request is still an ordinary application request.

It can experience:

* network latency
* database latency
* memory pressure
* CPU saturation
* HTTP errors
* container crashes
* infrastructure failures

OpenTelemetry can therefore provide the broader instrumentation layer.

```text id="y1h1q3"
                    Application
                         │
                  OpenTelemetry
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
      Metrics          Traces          Logs
          ↓              ↓              ↓
     Prometheus         Tempo           Loki
          └──────────────┼──────────────┘
                         ↓
                      Grafana
```

Meanwhile:

```text id="x4u7z2"
                  AI Application
                        │
                     Langfuse
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
       Traces        Prompts      Evaluations
```

These systems answer different questions.

Grafana can help answer:

> Why did this service become slower?

Langfuse can help answer:

> Why did this AI response become worse or more expensive?

Both are useful.

---

# AI Evaluation Becomes Part of Testing

This is one of the biggest differences between ordinary applications and AI applications.

Traditional software often has deterministic expectations.

```text id="h9zq5k"
Input
 ↓
Function
 ↓
Expected output
```

AI systems are probabilistic.

A response can be syntactically valid while being factually incorrect, irrelevant, unsafe, or inconsistent.

Therefore, AI applications need another layer:

```text id="7o5g3j"
Code tests
     +
Integration tests
     +
AI evaluations
```

An evaluation might measure:

* factuality
* relevance
* retrieval quality
* tool selection
* structured output validity
* hallucination rate
* safety
* latency
* cost

This makes Langfuse-style evaluation infrastructure an important component of the development lifecycle.

---

# The Development Loop Changes Again

The ordinary AI coding loop looks like:

```text id="w5q6xk"
AI Agent
   ↓
Code
   ↓
Compiler
   ↓
Tests
```

An AI application adds another loop:

```text id="2h9f5c"
AI Application
      ↓
Evaluation
      ↓
Langfuse
      ↓
Identify regression
      ↓
Modify prompt / code / retrieval
      ↓
Evaluation again
```

Now there are effectively two AI systems to evaluate.

The first is the **coding agent** building the application.

The second is the **AI application** being built.

Both benefit from explicit context, constraints, and feedback.

# AI Applications Need More Than Model Observability

A production AI system should ideally be observable across the entire request.

Consider:

```text id="q7v3kn"
User request
     ↓
API
     ↓
Authentication
     ↓
Retrieval
     ↓
PostgreSQL
     ↓
Embedding search
     ↓
Prompt construction
     ↓
LLM
     ↓
Tool call
     ↓
LLM
     ↓
Response
```

A useful trace should allow an engineer to understand this entire chain.

That means the application needs to connect traditional infrastructure telemetry with AI-specific telemetry.

The goal is not merely knowing that an LLM request took two seconds.

It is understanding **where those two seconds went**.

---

# Cost Becomes Another Production Metric

AI applications introduce an operational dimension that conventional applications often do not have to the same degree: per-request model cost.

A request may involve:

```text id="l3b4fy"
Input tokens
+
Retrieved context
+
Tool calls
+
Output tokens
+
Multiple model invocations
```

An agentic workflow might invoke a model five or ten times for a single user request.

Therefore, observability should eventually allow the team to correlate:

```text id="3j5b0x"
User request
     ↓
Latency
     ↓
Tokens
     ↓
Model calls
     ↓
Cost
     ↓
Outcome
```

This makes AI observability part of both engineering and business operations.

---

# The Vector Database Should Not Become an Architectural Religion

pgvector is a useful starting point, but it should not be treated as a permanent requirement.

The same principle from the underlying architecture applies:

> **Specialize when the workload requires specialization.**

Start with:

```text id="9c2r7p"
PostgreSQL
 + pgvector
```

If the workload eventually demands a dedicated vector system because of scale, latency, indexing requirements, or operational characteristics, introduce one.

The application should abstract retrieval behind a clear interface so that the underlying implementation can change.

For example:

```text id="d2f1f5"
AI Application
      ↓
Retriever interface
      ↓
┌───────────────┐
│   pgvector    │
└───────────────┘
```

can later become:

```text id="8m1w0r"
AI Application
      ↓
Retriever interface
      ↓
┌───────────────────────┐
│ Dedicated vector DB   │
└───────────────────────┘
```

The application should not need to be rewritten around the database.

---

# AI Infrastructure Should Remain Part of the Monorepo

The same monorepo philosophy applies to AI functionality.

A possible structure might be:

```text id="q3f7xa"
/apps
  /mobile
  /web
  /api

/packages
  /ui
  /database
  /types
  /validation
  /ai

/services
  /workers
  /agents
  /ingestion

/infrastructure
  /terraform

/observability
  /dashboards
  /evaluations
  /alerts
```

The AI package might contain:

```text id="x5b9q1"
packages/ai/
├── models/
├── prompts/
├── agents/
├── retrieval/
├── tools/
├── evaluations/
└── schemas/
```

Now the coding agent has access to the AI system's implementation alongside the rest of the application.

Prompts, schemas, tools, retrieval logic, and evaluations become code that can be reviewed, tested, and versioned.

---

# Prompts Should Be Treated Like Code

Prompts are often treated as configuration.

For serious applications, that distinction becomes less useful.

A prompt can influence:

* model behavior
* output quality
* tool selection
* safety
* cost
* application behavior

Therefore, prompts should be:

* version controlled
* tested
* evaluated
* associated with model versions
* observable in production

A prompt change should be capable of going through the same development process as a code change.

```text id="7n5m0q"
Prompt change
     ↓
Git
     ↓
CI
     ↓
AI evaluation
     ↓
Staging
     ↓
Production
```

This is another reason to keep AI functionality close to the rest of the application.

# Terraform Completes the AI Application Infrastructure

Eventually, the infrastructure supporting an AI application can become substantial.

You may have:

```text id="2w8g3h"
AWS
├── Compute
├── PostgreSQL
├── Storage
├── Networking
├── Secrets
├── Queues
├── Monitoring
```

Terraform allows those resources to become part of the same development model.

```text id="q2m9zt"

+
AI configuration
+
Database schema
+
Infrastructure
+
CI/CD
```

can all be version controlled.

The AI agent can therefore understand not only how the application works, but also the infrastructure on which it operates.

# The Architecture Has Three Feedback Loops

The most interesting property of this architecture may be the feedback loops.

### 1. Coding feedback

```text id="1m6b7f"
AI coding agent
      ↓
Code
      ↓
Compiler / Tests / CI
      ↓
Feedback
```

### 2. Application feedback

```text id="8c3d1a"
Production application
      ↓
Telemetry
      ↓
Grafana / Langfuse
      ↓
Engineering feedback
```

### 3. AI quality feedback

```text id="r9v4k2"
AI application
      ↓
Evaluation
      ↓
Langfuse
      ↓
Prompt / retrieval / model changes
      ↓
Evaluation
```

These loops operate simultaneously.

The coding agent improves the software.

Observability tells engineers how the software behaves.

AI evaluation tells engineers how the AI behaves.

Together, they create a continuous development and improvement system.

---

# The Principle of Progressive Specialization

The architecture should not attempt to predict the future.

It should provide a path toward it.

Start with:

```text id="7z1n5d"
TypeScript
Expo
tRPC
Prisma
PostgreSQL
pgvector
```

Then add infrastructure as requirements emerge:

```text id="x2f8a9"
Redis
Kafka
dedicated vector infrastructure
specialized compute
additional services
```

The important thing is that each addition solves a demonstrated problem.

This avoids building a distributed system simply because a large company uses one.

The goal is not maximum infrastructure.

The goal is **minimum complexity necessary to meet the application's actual requirements**.

# The Larger Idea

The architecture described here follows the same principle as the monorepo architecture from the previous article.

The objective is to make the entire system understandable to both humans and machines.

The application contains:

```text id="4x9n2c"
Code
Types
API contracts
Database schemas
Prompts
AI workflows
Retrieval
Evaluations
Infrastructure
Tests
Observability
```

All of these can be versioned, inspected, tested, and increasingly automated.

That changes the role of AI in software development.

The AI agent is no longer simply generating a React component or writing an API endpoint.

It can potentially reason across:

```text id="u2j7kp"
Application
    ↓
Data
    ↓
AI
    ↓
Infrastructure
    ↓
Observability
    ↓
Evaluation
```

The architecture becomes the context in which the agent operates.

And the more explicit that architecture is, the less the agent has to guess.

## Conclusion

A modern AI application does not need to abandon the principles of a well-designed full-stack application.

A monorepo can provide context.

TypeScript can provide compile-time constraints.

tRPC can provide typed API contracts.

Prisma can connect application code to PostgreSQL.

pgvector can provide an initial retrieval layer without introducing another database.

LangChain and LangGraph can provide AI application primitives.

Langfuse can provide AI-specific tracing and evaluation.

OpenTelemetry, Prometheus, Tempo, Loki, and Grafana can provide broader application observability.

Terraform can make infrastructure reproducible.

CI/CD can connect all of these pieces into a controlled deployment process.

The result is an architecture where the AI system itself becomes another strongly integrated part of the application rather than a separate technology stack bolted onto it.

The broader principle remains the same:

> **Build systems that expose context, enforce contracts, generate feedback, and allow complexity to grow only when the application actually requires it.**

That architecture is useful for human developers.

It may be even more useful for the AI agents increasingly participating in building and operating the software.
